# 方案撰写（Solution Proposal）

从诊断到方案的桥：把痛点清单转化为分期、可验收的落地设计。

## 何时使用

- ANC 诊断完成，需要给客户提交解决方案或立项提案
- 客户要求「出个方案」但尚未明确范围，需要先给框架再迭代
- 已有历史方案，需要按新客户画像做定制改写

## 前置输入（先取证据再动笔）

1. `get_diagnosis` 读诊断结论（分层 / 三关评分 / 高风险项）——方案必须与诊断一致
2. `recommend_scenarios` + `recommend_reasons` 获取匹配的 AI 场景与推荐理由
3. `get_client` 确认客户分层：30 人以下做「降本增效型」轻方案；30-200 人做「进步型」标准方案；更大或央国企做「战略型」分期方案
4. `get_upstream_deliverables` 查上游阶段交付物，避免口径冲突
5. `search_knowledge` 检索同行业历史方案作参考（有则引用，无则说明为首次设计）

## 方案六段结构

1. **背景与目标**：客户现状一句话 + 可量化的成功标准（不许写「提升效率」这类空话，要写「报表制作从 2 天缩到 2 小时」）
2. **现状诊断摘要**：引用诊断结论，突出 Top 3 痛点与根因
3. **方案设计**：一期一场景，写清「输入 → AI 做什么 → 输出 → 谁使用 → 替代/增强哪个环节」
4. **分期计划**：试点期（1 个部门 1 个场景）→ 推广期 → 深化期；每期有明确里程碑与验收标准
5. **ROI 测算**：标注计算假设（工时成本、频率），给出保守 / 乐观两档
6. **风险与对策**：数据质量、人员抵触、供应商依赖、一把手支持度变化

## Guardrails

- 方案中每个承诺都要能追溯到诊断证据或客户原话；无证据的设计标「假设待验证」
- 不给无法兑现的量化承诺；ROI 必须写明假设条件，禁止只给乐观值
- 分层适配：小客户不套大方案（避免过度设计），央国企必须包含合规与数据安全章节
- 产出为草稿，须 FDE 审核后才能对外提交；需要生成正式交付物时用 `generate_deliverable`
