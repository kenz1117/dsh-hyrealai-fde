# 人机分工与信任边界外移（执行权交 AI、判断权责任留人）

## R — 原文

> "当前阶段 AI Native 更准确的形态并不是'AI 替代人'，而是把执行权逐步交给 AI，把判断权和责任留在人手中，并通过工程系统明确两者之间的边界。"（阿里云手册 1.1 案例一「反思」）

## I — 自述

人与 Agent 的协同是信任边界不断外移的过程，分三阶段，每阶段边界、人的职责、平台必须补齐的能力各不同：本地辅助期——边界在人，人做一切决策，平台只需工具级集成；云端自主期——边界扩到运行时/仓库/任务系统，人定目标与验收，平台必须补运行时隔离、权限、审计；多 Agent Team 期——边界扩到工具链/任务状态/跨系统授权，人负责目标与最终责任，平台必须补机器可执行护栏与跨系统授权协议。总的三分原则：系统负责状态、权限、规则等高确定性事务；AI 负责约束内的分析、生成与长程执行；人负责目标设定、关键决策、风险取舍和最终责任。关键纪律：放开权限不按"模型够强"判断，按"平台护栏是否先于信任到位"判断；数字员工不能成为绕过权限与责任体系的捷径。

## A1 — 书中案例

- 数字投手的职责收拢：即便数字员工已能承担越来越长的执行链路，"目标设定、业务门槛定义、发布门禁以及高风险决策仍然需要人承担"；人的角色从执行收拢到 Loop 维护与寻找真需求，交付周期反而从 10 天缩到 2 天。（阿里云手册 1.1）
- 操作分级实例：搜索代码→交集内自动放行；查询日志→签发短时只读凭证；改测试环境配置→结构化授权请求等用户确认；重启生产实例→必须资源负责人或值班负责人审批，"不能由 Agent 自行确认"。（阿里云手册 3.3.1）

## A2 — 未来触发

使用情境：
1. 决策"什么时候可以放手让 Agent 操作生产环境"；
2. 设计数字员工治理路线图或人机分工界面；
3. 争论"AI 替代人还是辅助人"需要可操作的分工框架。

语言信号：中："哪些能交给 Agent 做""信任边界/放权条件""人机分工怎么划""谁对结果负责"；英："human-AI division of labor", "trust boundary", "delegation to agents", "accountability"。

与相邻能力区分：本卡是**分工阶段与放权条件的治理框架**；权限五原则（agent-permission-principles）是**授权体系的工程实现**；云上 Scrum（digital-employee-evolution）讲**协作组织形态**而非放权边界。

## E — 执行步骤

1. 定位当前信任边界阶段：本地辅助/云端自主/多 Agent Team，对照该阶段平台必备能力清单查缺。完成标准：阶段结论 + 缺失能力清单。
2. 按三分原则画分工界面：状态/权限/规则归系统，分析/生成/长程执行归 AI，目标/关键决策/风险/责任归人。完成标准：界面表经业务与安全双方确认。
3. 给每类操作定放行级别：自动放行/结构化授权请求/人工审批。完成标准：高风险操作（生产变更、资金、数据出域）全部落在人工审批档。
4. 外移前置条件检查：护栏（复合身份、权限收敛、可撤销可追溯）到位才外移下一档。完成标准：护栏清单齐备且有审计记录。

## B — 边界

反场景：拿"实习生比喻"当放权依据——"像人一样管理"只能用一半，机器可执行护栏必须先于信任到位；组织还没想清楚目标与验收标准时先别扩边界。失败模式：数字员工成为绕过权限与责任体系的捷径；误以为自动化消除了协调成本（只是转移到目标定义与发布门禁）。作者盲点：三阶段是线性叙事，实际组织会因事故回退，回退机制与信任重建书中未讨论；"责任留人"在法律与考核层面如何落到具体个人，表述仍停留在原则层。
