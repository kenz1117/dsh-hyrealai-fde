# Guardrail 三态协议（PASS/BLOCKED/UNKNOWN + Evidence）

## R — 原文

> "Guardrail 不理解业务语义，只执行确定性的协议约束并聚合最终结果：必检项缺失，或者存在 BLOCKED / UNKNOWN 时，不能形成可放行结果；只有所有必选检查都提交 PASS，最终门控结果才可能为 PASS。"（阿里云手册 3.3.2 Guardrail）

## I — 自述

这是高风险生产动作（发布、配置变更）的机器侧门控协议，与人侧的质量门禁构成对称物。协议对象 GuardrailRun = 固定版本 Spec（定义必检项与三态判定）+ 不可变 ChangeSet + 递增 Submission + 门控结果。三态定义：PASS 表示 Agent 判断证据充分满足通过条件；BLOCKED 表示发现明确阻断事实；UNKNOWN 表示因查询失败、证据不足或事实无法解释而不能可靠判断——UNKNOWN 不会被当作 PASS。三个分离原则：稳定安全意图（规则维护者定义）与开放执行（Agent 自主选择调查方式）分离；规则更新不改写历史判断依据（固定版本 Spec）；事实-证据-动作绑定——现场状态变化则原结论失效。Agent 不能自行选择更宽松的规则解释；证据不足或生产现场已变（ChangeSet 比对）即拒绝自动执行。本质：由确定性系统做门禁，不能只依赖提示模型记得遵守。

## A1 — 书中案例

- 发布门禁 Spec 示例（阿里云 3.3.2）：Spec 含 description"检查本批配置是否收敛，以及受影响应用是否健康"、instructions"必须使用本次 ChangeSet；查询失败、数据不足或无法解释时返回 UNKNOWN"、validForSeconds: 300（超时失效）；每个 Check 逐项提交三态结果与 Evidence（来源、观测时间、查询范围、结果摘要或失败原因），Guardrail 机械聚合。Agent 报告"所有检查项都通过"却无 Evidence 时，无证据的"通过"按 UNKNOWN 处理，不放行。

## A2 — 未来触发

使用情境：
1. 设计 Agent 自动执行生产操作（发布/变更）的安全门禁；
2. Agent 自报"检查都通过了"但要判断能不能放行；
3. 把人侧门禁（如项目质量门禁）自动化为机器协议。

语言信号：中："发布门禁/变更门禁""三态/UNKNOWN 怎么处理""无证据不放行"；英："guardrail protocol", "PASS BLOCKED UNKNOWN", "evidence-based gate", "release gating"。

与相邻能力区分：本卡是**机器侧协议设计**；质量门禁（四重九式内的 G1–G9）是**人侧项目门禁**——两者对称但对象不同；权限五原则（agent-permission-principles）管**授权**，本卡管**放行前的检查证据**。

## E — 执行步骤

1. 写固定版本 Spec：列出必检项、每项三态判定规则、有效期。完成标准：Spec 经规则维护者评审定版。
2. 约定 Evidence 格式：来源、观测时间、查询范围、结果摘要或失败原因。完成标准：无 Evidence 的提交协议上不可能被判 PASS。
3. 实现机械聚合：必检项缺失或含 BLOCKED/UNKNOWN 即不放行；执行前重查现场状态。完成标准：聚合逻辑不含语义解释，可单测验证。
4. 变更场景绑定 ChangeSet：现场已变即原结论失效重跑。完成标准：ChangeSet 比对生效，过期 Submission 不能复用。

## B — 边界

反场景：低风险只读操作（搜索、查询）逐项走三态是过度工程；把 Guardrail 当业务正确性评审——它不理解业务语义。失败模式：只依赖提示模型记得遵守规则；允许 Agent 自选更宽松的规则解释；把 UNKNOWN 静默降级为 PASS。作者盲点：协议假设存在"规则维护者"角色与可固化的检查口径，检查口径本身如何演进、Spec 冲突时谁仲裁，书中未展开；UNKNOWN 强制显性化会推高人工复核量，成本影响未量化。
