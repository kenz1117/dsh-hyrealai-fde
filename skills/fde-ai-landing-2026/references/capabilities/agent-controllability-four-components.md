# Agent 可控性设计（数字投手四组件）

## R — 原文

> "项目初期，团队没有采用纯 ReAct 模式构建数字投手。原因在于，Agent 擅长推理，但'能推理'并不等于'可控'，而广告投放场景对确定性、可解释性和执行安全都有很高要求。因此，团队从一开始就围绕'如何约束 Agent 的自由度'进行设计。"（阿里云手册 1.1 案例一·产品基建）

## I — 自述

高确定性场景的 Agent 架构第一设计目标不是"更自主"，而是"约束自由度"。把 Agent 拆成四个组件：投手经验——把专家经验预提炼为结构化结论（存在什么问题、证据、处方、成立条件），管"该做什么"，头脑不必运行时重新研究；投手脚脚——由最接近事实的系统预计算状态、权限、参数约束，产出明确的可操作清单（当前能做什么、需满足什么条件、失败如何恢复），管"能做什么"；投手头脑——只综合经验、能力、意图与业务围栏做推理取舍，在受限空间内执行且决策可解释，管"怎么选"；投手评测——黄金用例做测试集、综合评分表做标准、红线问题一票否决，管"做对没有"。总原则：确定性的部分尽量交给工程，推理只发生在可控空间内；与其堆 Skill，不如沉淀可复用工作流。

## A1 — 书中案例

- Alibaba.com 数字投手：拒绝纯 ReAct，按四组件建可控调控链路（经验=问题/证据/处方；手脚=状态/权限/可操作项；头脑=客户意图/业务围栏/推理取舍；评测=黄金用例/综合评分/红线否决）。对反向操作、数据错误等红线问题采用一票否决。上线后效果低于预期的部分转向数据闭环校准业务正确性——架构解决"能不能做"，闭环解决"做得对不对"。（阿里云手册 1.1）

## A2 — 未来触发

使用情境：
1. 设计金融、广告投放、生产调控等高确定性 Agent；
2. Agent 直连大模型自由决策，出过几次反向操作/事故要收口；
3. 评审 Agent 方案，判断自由度是否失控。

语言信号：中："Agent 不可控/乱操作""别用纯 ReAct""怎么约束 Agent 的自由度""评测集/红线"；英："agent controllability", "constrained agent architecture", "guardrail evaluation", "ReAct vs workflow"。

与相邻能力区分：本卡管**单个 Agent 的架构层自由度约束**；Guardrail 三态协议（guardrail-tri-state）管**生产动作放行时的门控协议**；权限五原则（agent-permission-principles）管**授权体系**——三者是架构/门禁/权限三个层面。

## E — 执行步骤

1. 盘点业务对确定性/可解释性/安全的要求等级，决定是否禁用纯 ReAct。完成标准：写出要求等级结论与架构选型（四组件 or 自主 Agent）。
2. 把领域专家结论预提炼为结构化经验组件（问题/证据/处方/条件）。完成标准：经验组件可被头脑直接消费，无需运行时研究。
3. 把系统状态、权限、参数约束预计算为可操作清单。完成标准：头脑收到的每个动作项都有条件与恢复路径。
4. 建评测体系：黄金用例集 + 综合评分 + 红线一票否决。完成标准：最小可用评测集上线，红线清单经业务方确认。

## B — 边界

反场景：探索型任务（研究、创意发散）用四组件会过度约束；低风险内部工具不必全套上。失败模式：靠提示词约束代替工程收口——"确定性的部分尽量交给工程"是硬原则，提示词约束不是；评测从零开始求全，应从最小可用集起步随真实业务补充。作者盲点：四组件方案依赖充足的预计算基建与专家经验存量，冷启动场景（没有结构化经验、系统不可预计算）怎么起步，书中未给出路径。
