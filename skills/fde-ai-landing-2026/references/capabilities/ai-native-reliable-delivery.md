# AI Native 可靠交付四环节（项目理解/需求理解/可靠编码/线上排障）

## R — 原文

> "通过 3 个多月的实践，团队在研发效率……方面有了长足进步：平均交付周期缩短一半，千行代码缺陷率下降 70%，变更失败率下降 90%+。"（阿里云手册 1.2 案例二·千问用增 Agent）

## I — 自述

团队用 AI 写代码又快又多，交付效果却被四件事卡住，由此收敛出 AI Coding 的四个能力环节，每个环节配机制与沉淀资产：项目理解——Code Docs 解释"为什么这么设计"、Code Graph 精确查询影响面、Rules 固化团队经验，产出项目文档与代码图谱；需求理解——AI 主动追问隐含决策（如"生成公开分享链接"背后的撤销机制、访问控制、数据一致性），沉淀 Spec/Tasks 与验收场景；可靠编码——TDD 固定边界，并发场景下注意链路幂等而非仅接口层幂等；线上排障——统一 TraceId 固定证据采集，形成线上证据链与诊断能力。递进关系是关键：项目理解不准→需求再详细也走错方向；边界不明确→代码越快风险越大；缺乏验证→分不清稳定能力还是偶然结果。目标不是提升代码生成速度，而是让 AI 基于真实上下文、明确需求和可验证反馈持续完成复杂任务。

## A1 — 书中案例

- 千问研发团队约 15 名服务端工程师全栈 AI Coding，经粗放探索（部分场景生成速度达传统数倍甚至约 10 倍）→标准化与存量工程适配（边际收益下降，转方法标准化）→提升 SDLC 覆盖度三阶段。3 个多月后：平均交付周期缩短一半、千行代码缺陷率下降 70%、变更失败率下降 90%+。（阿里云手册 1.2）

## A2 — 未来触发

使用情境：
1. 企业要建 AI Coding 体系，问从哪里入手、分几步；
2. Agent 改代码快但线上事故反而增多，要定位哪个环节缺失；
3. 评估"接入了 AI 工具"之后还缺什么。

语言信号：中："AI 写代码不可靠""Code Graph/Spec/TDD/TraceId""AI Coding 体系怎么建"；英："reliable AI coding", "code graph impact analysis", "spec-driven development", "AI debugging"。

与相邻能力区分：本卡是**AI Coding 工程能力建设路线**（四个环节）；上下文资产三件套（context-assets-trio）是其中一个环节背后的**知识资产结构**；环境与验证驱动（env-verification-driven）是**投资杠杆点的判断逻辑**，不展开环节机制。

## E — 执行步骤

1. 按事故归因过筛四环节：原因不明→排障缺 TraceId 证据链；改错位置→项目理解缺 Code Graph；需求误解→缺 Spec 前置澄清；越快越险→缺 TDD 边界。完成标准：指出最薄弱环节及证据。
2. 补项目理解资产：建 Code Docs + Code Graph + Rules。完成标准：Agent 可查询影响面，团队经验有成文 Rules。
3. 需求入口强制 Spec：AI 主动追问隐含决策，沉淀 Spec/Tasks。完成标准：每个任务有验收场景。
4. 建排障证据链：统一 TraceId，证据采集固定化。完成标准：任一线上问题可按 TraceId 还原证据链。

## B — 边界

反场景：单点接入工具即宣称转型完成——"让 Agent 能用"只是起点；个人开发者随手用 AI 写脚本不需要全套四环节。失败模式：度量只有 AI 代码占比这类使用量指标（激励无效生成）；工具仍面向人而非 Agent（返回日志地址而非结构化结论），链路层层中断。作者盲点：四环节实证来自千问团队这类模型厂内部（工具链与模型能力天然对齐），外部企业照搬时模型与基建错配的落差书中未充分展开。
