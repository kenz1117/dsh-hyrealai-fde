# secrets 永不物化（Credential Broker 模式）

## R — 原文

> "生产环境处理不可信代码时，应让 Sandbox 只持有占位值，由可信的出站代理在请求匹配模型 API 的域名、路径和方法后注入真实凭据。"（阿里云手册·Sandbox 凭据边界）

> "P0 原则：secrets 永远不物化（never materialize）"（ANC 架构·运行时治理原则）

## I — 自述

这条原则是 Agent 时代凭证安全的绝对红线：真实密钥/凭证绝不进入模型上下文、Agent 进程、插件、沙箱环境变量或普通日志——"物化"（materialize）意味着密钥出现在快照、日志、上下文窗口这些无法追回、可能被复制的地方。替代方案是代理与注入：优先级排序为代理调用（出站代理持有真实凭据，按域名/路径/方法匹配后转发）＞注入短期凭证（Credential Broker 代管长期凭证、按需兑换短时凭证）＞注入长期凭证（仅限无法代理的场景）。配套工程细节：凭据状态不进快照，沙箱恢复后由控制面重新注入；每条注入的凭证应绑定目标服务、只读/最小动作、短时效与当前实例。与"最小权限"常识的区别在于绝对化：不是"少暴露"，而是"永不出现"。

## A1 — 书中案例

- 阿里云 OpenCode + OpenSandbox 示例：为了便于本地运行，示例通过环境变量把 API Key 传入 Sandbox；但生产环境处理不可信代码时必须改为"Sandbox 只持有占位值，由可信的出站代理注入真实凭据"——同一套代码，本地演示与生产执行走两条凭证路径。（阿里云手册·Sandbox 示例）
- 角色四件套中的 Credential Broker：凭证代理，代管长期凭证并按需兑换短期凭证；Agent 查询目标服务日志时，系统"签发只对准目标服务、只读、短时、绑定当前实例的访问凭证"。（阿里云手册 3.3.1）

## A2 — 未来触发

使用情境：
1. 给 Agent/沙箱配 API key 时判断怎么给才安全；
2. Agent 平台的快照/日志/上下文会不会泄露凭证；
3. 设计 Agent 出站调用链路的凭证注入点。

语言信号：中："密钥不能给 Agent""凭证怎么注入""沙箱环境变量安全吗""短期凭证/凭证代理"；英："secrets never materialize", "credential broker", "ephemeral credentials", "outbound proxy"。

与相邻能力区分：本卡是权限五原则（agent-permission-principles）第四原则的**专深展开**，专注凭证不在何处出现、如何注入；权限五原则管整个授权体系（身份/收敛/决策/审计），不重复展开注入细节。

## E — 执行步骤

1. 盘点物化面：排查真实密钥出现在哪些位置（上下文、进程环境变量、沙箱、快照、日志）。完成标准：物化位置清单齐备，标注每处能否消除。
2. 按优先级改造：能走出站代理的改代理调用；不能的改 Credential Broker 短期凭证注入；长期凭证注入仅留白名单。完成标准：无白名单外物化点。
3. 凭证绑定约束：每条短期凭证绑定目标服务、最小动作、短时效与当前实例。完成标准：抽查凭证均可回答"对什么、能做什么、多久有效"。
4. 快照与恢复检查：凭据状态不进快照，恢复后由控制面重注入。完成标准：从快照恢复的实例中搜不到真实密钥。

## B — 边界

反场景：纯本地个人开发（代码与密钥同trust域）不必全套代理链路；把这条原则误用于"客户业务数据的出域控制"——那是数据安全六准则与 IP 主权的地盘。失败模式：为调试方便给沙箱配长期高权限 key（物化后随快照/日志泄露且无法追回）；凭据状态随快照恢复而复活。作者盲点：出站代理与 Broker 本身成为新的单点与信任汇聚处，其自身被攻破的缓解（代理的密钥轮换、代理审计）在两份文档中都只有一句带过；对已有系统存量物化的清理成本未讨论。
