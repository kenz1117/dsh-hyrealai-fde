# Agent 权限五原则与有效权限交集公式

## R — 原文

> "Agent 可以规划行动，但不能自行创造权限。每一次实际操作，都应建立在可验证的身份、明确且逐步收敛的委托、独立于模型的策略决策，以及不向 Agent 暴露长期凭证的执行路径之上。"（阿里云手册 3.3.1 权限体系）

## I — 自述

Agent 授权体系的五条原则：①可验证复合身份——区分"这是哪个 Agent、哪个实例、代表谁、为何执行"；②权限只能逐级收敛——用户有权 ≠ Agent 自动有权代为执行，多 Agent 协作每跳都建自己的身份，子委托范围只能比上游更小；③确定性系统决策、在靠近资源处执行——"允不允许"由 PDP 判断，PEP 分布在 Runtime/网关/MCP Server/资源服务多层，入口允许不是下游省略校验的理由（MCP 解决协议互通，不自动解决授权）；④长期凭证不进 Agent——经 Credential Broker 兑换短期凭证；⑤可撤销可追溯——审计把意图→委托→决策→凭证→结果连成完整链路。可计算的表达式：有效权限 = 用户权限 ∩ Agent 能力上限 ∩ 平台策略 ∩ 本次委托范围 ∩ 运行时约束。授权结论三态：允许 / 拒绝 / 需要补充授权（Challenge——结构化授权要求，不是让模型去猜的 403 文本）。核心分工是意图与授权分离：Agent 决定下一步想做什么，系统独立决定它是否有权这样做。

## A1 — 书中案例

- 操作分级表（阿里云 3.3.1）：搜索相关代码和只读文档→在用户权限、Agent 能力和只读基线策略的交集内自动放行；查询目标服务日志→签发只对准目标服务、只读、短时、绑定当前实例的访问凭证；修改测试环境配置→暂不执行，返回结构化授权请求；重启生产实例→要求资源负责人或值班负责人审批，不能由 Agent 自行确认。
- 主 Agent 委托子 Agent 的判定：子委托范围只能比上游更小，且"允不允许"不由子 Agent 或主 Agent 自判，由 PDP 在靠近资源处重新校验——委托链每深一层，五层交集只会更窄。

## A2 — 未来触发

使用情境：
1. 设计 Agent/数字员工的身份与权限体系；
2. 多 Agent 委托链场景，问子 Agent 权限怎么给；
3. Agent 请求被拒时如何返回"结构化的补充授权要求"。

语言信号：中："Agent 权限怎么管""身份/授权/委托""最小权限/逐级收敛""凭证兑换"；英："agent permissions", "least privilege delegation", "PDP PEP", "credential broker"。

与相邻能力区分：本卡是**授权体系的工程原则与公式**；信任边界外移（trust-boundary-shift）是**放权节奏的治理框架**；secrets 永不物化（secrets-never-materialize）是其第四原则的**专深展开**。

## E — 执行步骤

1. 建身份层：为 Agent 建稳定身份 + 运行实例 + 任务上下文三层主体，代表用户时附委托依据。完成标准：任一请求可回答"谁在行动、代表谁"。
2. 实现交集校验：有效权限按五层交集计算，子委托 ≤ 上游。完成标准：委托链上每层可查询其交集范围。
3. 部署 PDP/PEP：决策集中、执行靠近资源，入口允许不豁免下游校验。完成标准：资源服务对每个请求独立鉴权。
4. 补三态与审计：拒绝返回结构化授权要求；审计链覆盖意图到结果。完成标准：抽查任一历史操作可完整还原链路并可撤销。

## B — 边界

反场景：个人本地开发助手无需全套 PDP/PEP；把权限体系当成替代业务评审的银弹。失败模式：让 Agent 自判"允不允许"；用 403 文本让模型猜下一步；MCP Server 完成 OAuth 登录后不再逐工具鉴权。作者盲点：五原则落在阿里云级平台基建上（可信 Runtime、统一身份服务），中小组织没有现成 PDP/PEP 时的最小可行替代方案书中未给出；交集公式是设计约束，缺乏对执行点性能与体验成本的量化讨论。
