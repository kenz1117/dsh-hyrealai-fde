# 数据闭环 1–10 与双 Loop（经验 Loop / 手脚 Loop）

## R — 原文

> "项目上线后，团队发现实际调控效果仍低于预期。复盘后意识到，这套原则上成立的技术架构主要解决了'能不能做'的问题，却没有充分解决'业务上做得对不对'的问题。"（阿里云手册 1.1 案例一·产品基建转数据闭环）

## I — 自述

产品基建解决"能不能做"（0→1），数据闭环解决"做得对不对"（1→10）。五步闭环：线上执行→分层评测（把执行漏斗分层、定位 bad case 集中在哪层）→归因诊断（策略错还是能力缺）→快速补给→能力上线，新轨迹再回流。补给走两条线：经验 Loop——策略假设经工程化上线，策略挖掘与策略生产拆给两个数字员工、以结构化契约交接；手脚 Loop——线上失败轨迹是输入不是废料，聚类定位根因、补齐能力后回归评测，失败轨迹直接 Skill 化（约 80% 核心能力由此而来）。判断闭环是否真闭合的试金石：触发与校验还依赖人，就说明没闭合。

## A1 — 书中案例

- 数字投手转向数据闭环后：经验 Loop 使策略交付周期从约 10 天缩短至 2 天；手脚 Loop 使约 80% 核心能力 Skill 化，复杂任务服务成功率显著提升。（阿里云手册 1.1）
- 反例补充：万有无界平台 auto bug fix 一次成功率 89%，但 bug 日清率仅从 53% 升到 63%——"分析下来整体的触发依赖人或者其他确定性流程来完成"，闭环未闭合。（阿里云手册 1.3）

## A2 — 未来触发

使用情境：
1. Agent 产品上线后效果停滞，想加功能前先找对杠杆；
2. 设计线上 bad case 的归因与补给机制；
3. 决定失败案例是"修掉扔掉"还是变成能力建设输入。

语言信号：中："bad case 怎么归因""效果停滞不涨""失败轨迹/Skill 化""数据闭环怎么建"；英："data flywheel", "bad case triage", "failure-to-skill pipeline", "eval loop"。

与相邻能力区分：本卡管**上线后效果持续提升的运营机制**；四组件卡（agent-controllability-four-components）管**上线前的可控架构**；知识飞轮治理（knowledge-flywheel-governance）管**组织级知识资产的审批与真相源**，不是单产品的效果闭环。

## E — 执行步骤

1. 建分层评测：把线上执行漏斗按环节分层，统计 bad case 分布。完成标准：能回答"bad case 集中在哪一层"。
2. 逐类归因：策略错（该做什么错了）还是能力缺（做不了）。完成标准：bad case 全部归入两类并抽样核实。
3. 分流补给：策略假设走经验 Loop（工程化上线），能力缺失走手脚 Loop（聚类根因→补能力→回归评测）。完成标准：两条 Loop 各有承接人与交付节奏。
4. 检查闭环闭合度：统计触发与校验环节的人工依赖占比。完成标准：人工依赖占比可量化且有下降计划——依赖人即未闭合。

## B — 边界

反场景：0→1 还没完成（基建不稳、架构未立）时跑数据闭环是空转；一次性小项目没有足够线上轨迹支撑闭环。失败模式：只收集反馈不归因不补给（闭环开环）；把自动化修复率当流程指标——修复率 89% 日清率仍可原地踏步。作者盲点：双 Loop 案例来自自带海量线上流量的平台产品，长尾 B 端产品轨迹稀疏时分层评测的统计功效不足，书中未讨论小流量场景的替代方案。
