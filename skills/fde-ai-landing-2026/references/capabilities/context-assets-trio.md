# 上下文资产三件套（一个需求、一组事实）

## R — 原文

> "开发者可以逐项修好，但修复往往只留在当前机器。下一个 Agent 进入新实例，仍会重复这三次失败。第一个任务的预算同时花在业务修改和环境排查上，排查结果却没有成为项目的一部分。"（阿里云手册·Agent 环境管理）

## I — 自述

AI 时代的研发任务不是"派个活"，而是供给"一个需求、一组事实"：每个任务拆成三件相互依赖的事——上下文资产（说明解决什么问题）、工程执行环境（修改发生在哪里）、验证证据（证明结果成立），缺一环任务就不成立。上下文资产五类来源：产品文档、技术文档、设计文档、前后端真实工程、测试用例与测试证据（含 Skill、MCP、Markdown、Spec、Code Docs、Code Graph），每项资产标注来源、负责人、版本、适用范围。知识外置的理由：外部知识可更新、纠正、撤回、分级授权，模型参数里的知识做不到。闭环规则是灵魂：验证过程中发现的新事实必须回写沉淀到文档、代码、测试和规则中——不回写就不算资产，且资产开始腐化（文档不再可信）。

## A1 — 书中案例

- 万有无界平台：评审用基于真实代码的可交互原型（可检查正常/空/异常态/权限/数据依赖），近四个版本约 80% 交互体验类需求以 Git 可交互原型承接、50%+ 产品经理采用；测试转证据驱动修复（同版本同环境复现、回到相同页面状态验收），视觉类问题一次修复成功率约 89%；线上千行代码缺陷率千分之 0.01；30 余项共享技能、6–8 月调用超 2 万次。（阿里云手册 1.3）

## A2 — 未来触发

使用情境：
1. 组织要建"AI 友好"的知识库/上下文供给体系；
2. 发现不同任务反复出现相同环境报错、Agent 重复踩坑；
3. Agent 按过时文档执行还是按实际情况执行起争执。

语言信号：中："上下文/知识库怎么供""新事实要回写""环境问题重复出现""一个需求一组事实"；英："context assets", "knowledge externalization", "evidence-driven fix", "write-back"。

与相邻能力区分：本卡管**任务级的上下文供给结构与回写规则**；可靠交付四环节（ai-native-reliable-delivery）管**端到端工程能力建设**；知识飞轮治理（knowledge-flywheel-governance）管**组织级候选-审批-真相源治理**——回写之后进入谁的地盘由后者管。

## E — 执行步骤

1. 任务启动时检查三件套齐备度：需求说明、执行环境、验证证据各是什么。完成标准：三者齐备才开工，缺项显式标记。
2. 盘点上下文资产：按五类来源清点，逐项补来源/负责人/版本/适用范围。完成标准：资产清单可按需组合出"一组事实"。
3. 建回写规则：验证发现的新事实回写文档/代码/测试/规则。完成标准：回写动作有固定入口（如 PR 模板勾选项）。
4. 定期抽检资产腐化：文档与实际行为是否一致。完成标准：抽检不一致项清零或标注失效。

## B — 边界

反场景：把文档堆当知识库——没有"按需组合的事实组"与回写闭环的文档堆不适用本卡；纯个人笔记管理也不适用。失败模式：环境排查逐次手工修但不沉淀（下一个 Agent 重复三次失败）；知识只留在个人机器上，人走经验走。作者盲点：回写规则默认执行者有治理意愿与工具支持，但员工"我说得越多被替代得越快"的藏匿焦虑（阿里云挑战五）会直接抽干回写输入，激励配套在案例中着墨不足。
