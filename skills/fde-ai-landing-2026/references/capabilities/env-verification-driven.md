# 环境与验证驱动（Spec 约束/假设二分）

## R — 原文

> "过去几个月模型能力跃升一度让大家兴奋，认为研发很快能完全托管给 AI，但深入真实业务后：环境搭不起来、上下文拼不全、验证跑不通、发布卡在流程上——大家逐渐从乐观转向务实。"（阿里云手册 2.3 挑战三：度量）

## I — 自述

AI 优先解决的是"反馈公开、验证可规模化"的问题，Coding 本身已接近被解决；所以主战场不在让模型更会写代码，而在把研发工作流改造成"有反馈、可验证"的环境。判断链：真实案例中 Coding 耗时占比已 <1% → 按阿姆达尔定律，优化非瓶颈环节得不到数量级收益 → 杠杆点在环境与验证。价值重心从代码（50–60%）迁移到环境与验证（40–50%）。电气化类比点破两种深度：电机替换蒸汽机是局部提效（Workflow 嵌入），单元驱动重构工厂是体系跃升（Agentic 自主闭环）。Spec 写法上做二分：约束（数据不能出域、接口向后兼容、延迟阈值——长期保存并尽可能自动检查）与假设（微服务还是单体、哪种缓存——允许 AI 根据实现和运行反馈自己调整）；Spec 划定"什么算对"的边界，不规定实现路径。

## A1 — 书中案例

- 千问团队三阶段实证杠杆点迁移：粗放探索期部分场景生成速度达传统约 10 倍，但随后"生成速度的边际收益开始下降"，重心转向标准化与存量工程适配、提升 SDLC 覆盖度——验证了写代码之外的环境与验证才是持续瓶颈。（阿里云手册 1.2）
- 换上最强模型后任务成功率没提升的反问：若瓶颈在环境（工具面向人、状态不可机读、验证跑不通），优化模型（非瓶颈）无收益，钱应投给 AI 友好基础设施——需求文档/数仓/接口/发布平台面向 Agent 重设计。（阿里云手册 2.1，基于 ce37 的工具面向人反例）

## A2 — 未来触发

使用情境：
1. 换了更强模型但 Agent 任务成功率没涨，决定预算投模型还是投基建；
2. 规划研发平台的投资优先级（AI 友好改造清单）；
3. 写 Spec 时纠结该规定多细。

语言信号：中："瓶颈不在模型""AI 友好基础设施""Spec 怎么写/约束与假设""验证跑不通"；英："AI-friendly infrastructure", "Amdahl bottleneck", "spec constraints vs assumptions", "verifiable feedback"。

与相邻能力区分：本卡是**投资杠杆点判断 + Spec 写法**；可靠交付四环节（ai-native-reliable-delivery）是**落地执行的具体环节机制**——先判断杠杆在哪，再按环节施工。

## E — 执行步骤

1. 找瓶颈：测量 Agent 任务失败集中在推理还是环境边界（工具调用、状态理解、验证执行）。完成标准：失败分布数据能指认瓶颈环节。
2. 若瓶颈在环境：列 AI 友好改造清单（文档/数仓/接口/发布平台面向 Agent 重设计）。完成标准：清单有优先级与责任人。
3. Spec 二分：逐条标注约束（自动检查）或假设（开放迭代），约束配自动检查项。完成标准：Spec 中无未分类条目，约束项有对应检查。
4. 补验证回路：让每个任务有可机器执行的反馈（测试/评测/门禁）。完成标准：任务成功率可度量且随环境改造上升。

## B — 边界

反场景：任务失败确实集中在模型能力（长尾推理错误）时，别拿阿姆达尔定律拒绝模型升级；一次性脚本无需 Spec 二分。失败模式：把"环境优先"当不换模型的借口——先测瓶颈再定投资；用 Demo 观感驱动转型决策而非度量。作者盲点：Coding 耗时 <1% 的证据来自头部平台团队，多数组织 Coding 占比仍高，直接套用"写代码不重要"会误判自身阶段；电气化类比是修辞不是数据。
